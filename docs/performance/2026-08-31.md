# Performance measurements — 31 August 2026

The changes reduce repeated main-actor work used by update badges, lists, source
labels, and inspectors. In the 2,000-app stress fixture, one primary update-count
read fell from **143.000 ms to 1.375 ms**, and the app/source/package lookup pass
fell from **8.687 ms to 4.522 ms**. These are local data-processing benchmarks,
not measurements of complete scan duration, launch time, or rendered frame rate.

## Method

- Baseline application source: `4a7307d226349fc4cf53bef27efb0539c087cd46`.
  The benchmark and correctness tests were added before changing application code.
- macOS 27.0 (26A5416b), arm64, Apple Swift 6.3.3, Swift Testing 6.1.3;
  `swift test -c release`. Both sides used the same machine, toolchain,
  fixture generator, and optimized configuration. Compilation is not timed.
- Each fixture has 200 or 2,000 apps, the same number of Homebrew packages and
  developer packages, and one skipped version per four apps. Half of Homebrew
  packages are matching casks; the rest are formula dependencies. Alphabetic
  product suffixes stay distinct under the app's digit-stripping normalization.
- One untimed warm-up and seven measured samples per size. The table reports
  medians. Counts and exclusion passes are each repeated 20 times per sample;
  their reported times divide the sample duration by 20.
- A lookup pass resolves each app's Homebrew match and sources, then resolves
  each cask's app. A rebuild reassigns both app and Homebrew inventories so the
  measurements include ongoing index-maintenance cost, not only warm reads.
- Assertions outside the timed regions check exact match totals, source totals,
  primary counts, and exclusions. Checksums match before and after for every sample.
- No network scans, package commands, or application updates are run by this
  benchmark. Settings use a temporary UserDefaults suite removed afterward.
  The app was closed during the reported runs. An earlier baseline taken while
  the app was launching was discarded and repeated with the app closed.
- This is a shared development machine, not an isolated performance lab. Medians
  and a second after-run help assess variability; small timing differences should
  not be treated as precise guarantees.

## Results

| Items per collection | Operation | Before median (ms) | After median (ms) | Reduction |
| --- | --- | ---: | ---: | ---: |
| 200 | App/source/package lookup pass | 0.786 | 0.396 | 49.6% |
| 200 | One primary update-count read | 1.542 | 0.129 | 91.7% |
| 200 | One exclusion pass over all app keys | 0.452 | 0.024 | 94.7% |
| 200 | Reassign app + Homebrew inventories | 0.399 | 0.481 | -20.5% |
| 2,000 | App/source/package lookup pass | 8.687 | 4.522 | 48.0% |
| 2,000 | One primary update-count read | 143.000 | 1.375 | 99.0% |
| 2,000 | One exclusion pass over all app keys | 46.365 | 0.289 | 99.4% |
| 2,000 | Reassign app + Homebrew inventories | 4.677 | 5.092 | -8.9% |

The second after-run confirmed the improvement: at 2,000 items, medians were
**1.152 ms** for a primary count, **3.810 ms** for the lookup pass, and **0.247 ms**
for an exclusion pass. The main table retains the first after-run rather than
selecting the faster repeat. All raw post-warm-up samples are retained in
[before.txt](before.txt), [after.txt](after.txt), and [after-repeat.txt](after-repeat.txt).
Across individual samples, one count read at 2,000 items ranged from
141.44–157.52 ms before, 1.26–1.43 ms after, and 1.12–1.19 ms in the repeat.
A third run verified the reusable shell runner after UI QA. It also passed with
matching checksums; at 2,000 items its medians were 1.631 ms for a count read,
5.323 ms for lookups, 0.332 ms for exclusions, and 6.569 ms for inventory
reassignment. Its samples are in [runner-validation.txt](runner-validation.txt).
This further illustrates host-load variability and the cache-maintenance tradeoff.

## Bottlenecks and changes

1. **Every exclusion lookup scanned the full exclusion array.** List filtering,
   update plans, and badges repeated this for each item. `AppSettings` now groups
   exclusions by item key whenever exclusions are saved. Lookups only inspect the
   matching group. Grouping preserves first-match ordering for duplicate persisted
   keys, and each read still checks expiry and skipped-version equality.
2. **The primary update count built the complete update plan.** That needlessly
   checked developer-package versions and filtered models, even though neither
   contributes to this count. `UpkeepStore` now supplies only apps, Homebrew, and
   macOS to the shared `UpdatePlan.primaryUpdateCount` calculation. Batch planning,
   cask deduplication, exclusion behavior, and installer/dependency rules stay intact.
3. **Indexed name matching still normalized input strings on every read.**
   `UpkeepLibraryState` now retains name variants already calculated while building
   its indexes. Names outside the current inventory use the original normalization
   fallback. Inventory reassignment clears and rebuilds the cache, preserving
   first-match ordering and handling renames, removals, and reordering.

The tradeoff is additional dictionaries bounded by the current inventory and
exclusion list. In the first after-run, inventory reassignment cost an additional
**0.082 ms** at 200 items and **0.415 ms** at 2,000 items. One subsequent lookup
pass alone more than offsets this cost in these fixtures. The repeat's rebuild
timing was within baseline variation, so no rebuild-speed improvement is claimed.
Peak memory, initial cold-cache population, and end-to-end startup were not measured.

## Reproduce

From the repository root on macOS:

```sh
./scripts/benchmark-performance.sh outputs/performance/current.log
python3 scripts/compare-performance.py \
  docs/performance/before.txt outputs/performance/current.log
swift test -c release
```

The runner builds an optimized test executable, then executes only the offline
benchmark. For a new before/after experiment, run it once before application source
changes and again afterward, keeping toolchain, fixture, and machine conditions
the same. To repeat an already-built benchmark without compiling:

```sh
UPKEEP_RESPONSIVENESS_BENCHMARK=1 swift test -c release --skip-build \
  --filter responsivenessBenchmark
```

`compare-performance.py` rejects missing/duplicate samples or mismatched result
checksums. Absolute times depend on hardware and load; no flaky wall-clock threshold
is added to normal tests. Normal tests skip the opt-in benchmark workload.

At the end of this measurement pass, no commit, push, notarized release, or
deployment had been performed. Subsequent Git publication is separate from these
local validation results.
