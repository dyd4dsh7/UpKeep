# Third performance pass — global search

Global search now normalizes its query once per calculation and avoids building
app-source and dependency strings when earlier fields already match. This pass
preserves the [first](2026-08-31.md) and [second](2026-08-31-services.md) passes.
The controlled comparison shows **10.8–24.4% less search-processing time** for
the larger fixture, with unchanged results and ordering.

## Bottleneck and changes

`GlobalSearchView` previously trimmed `store.searchText` inside every candidate
field comparison. Its variadic matcher also received eagerly constructed app
source labels and joined dependency lists, even when an item's name matched.
Source detection includes Homebrew/library lookups and source ordering.

The unchanged calculation was first extracted into `GlobalSearch` and benchmarked
before optimization. The view now uses that same model directly. The optimized
model retains one normalized query for the calculation and short-circuits costly
source/dependency work behind the earlier field checks. No persistent cache,
debounce delay, asynchronous state, or new invalidation rules were introduced.
Each view evaluation still searches the current inventories.

All seven groups, localized case-insensitive matching, localized natural name
sorting, newest-first history, result identities, and selection behavior remain
unchanged. Joined source/dependency strings remain searchable as a whole, including
queries spanning boundaries between values. No update/install, networking,
redaction, or package-manager behavior changed in this pass.

Application list sorting and diagnostics filtering were also inspected, but were
not changed or assigned speedup claims. Broad searches still filter and sort
matching inventories on each evaluation; this pass does not eliminate that work.

## Controlled results

Optimized Swift release builds on arm64 macOS 27.0 (26A5416b), Apple Swift 6.3.3,
Swift Testing 6.1.3. Each workload has one discarded warm-up and seven measured
samples. Times are medians in milliseconds. The app was closed during benchmarks.
Fixture creation, settings initialization, assertions, result-identity generation,
SwiftUI layout, rendering, and network operations are outside the timed region.
Filtering, field/string preparation, result allocation, and sorting are included.

Separate before/after runs showed substantial machine-load variation. To control
for that, a further benchmark executes the frozen original implementation and the
optimized implementation in the same process, alternating which runs first on
each sample. The table below uses those more conservative controlled results.
The reference is test-only and is not shipped in the app.

| Items per main collection | Query | Before median (ms) | After median (ms) | Reduction |
| --- | --- | ---: | ---: | ---: |
| 200 | name | 3.534 | 3.010 | 14.8% |
| 200 | missing | 4.203 | 3.205 | 23.8% |
| 200 | source | 4.622 | 3.709 | 19.8% |
| 200 | dependency | 4.886 | 3.982 | 18.5% |
| 2,000 | name | 45.900 | 40.946 | 10.8% |
| 2,000 | missing | 42.464 | 32.093 | 24.4% |
| 2,000 | source | 51.002 | 40.575 | 20.4% |
| 2,000 | dependency | 52.556 | 42.668 | 18.8% |

The size column means that many applications, Homebrew casks, developer packages,
and history records **each**, plus one adoptable app per four applications,
20 local models, and three macOS updates. Total records: 873 / 8,523.
Alphabetic product names avoid collisions in Homebrew's digit-stripping name
matching. Inventories include nil optional values, multiple app sources,
App Store management, and Unicode descriptions/recovery notes.

| Query | Search text | Results at 200 / 2,000 |
| --- | --- | ---: |
| name | `Product` with surrounding spaces/newline | 870 / 8,520 |
| missing | `no-such-result` | 0 / 0 |
| source | `GitHub` | 160 / 1,600 |
| dependency | `ssl zlib` (spans two dependency names) | 200 / 2,000 |

Every measured optimized result is checked for full value equality and ordering
against the original implementation across all seven groups, plus identity and
empty-state equality. The paired reference also checks its identity after timing.
Raw paired samples: [paired.txt](search/paired.txt).

## Original before/after runs and variability

The starting baseline included both earlier passes. The original search view
still matched commit `4a7307d226349fc4cf53bef27efb0539c087cd46`; extraction did
not change its matching logic. The following measurements were taken before and
after the optimization, using the same fixture and release configuration:

| Items per main collection | Query | Before median (ms) | After median (ms) | Reduction |
| --- | --- | ---: | ---: | ---: |
| 200 | name | 4.021 | 3.021 | 24.9% |
| 200 | missing | 4.817 | 3.167 | 34.2% |
| 200 | source | 5.519 | 3.719 | 32.6% |
| 200 | dependency | 5.875 | 3.928 | 33.2% |
| 2,000 | name | 53.907 | 41.409 | 23.2% |
| 2,000 | missing | 50.383 | 32.600 | 35.3% |
| 2,000 | source | 65.305 | 40.983 | 37.2% |
| 2,000 | dependency | 69.369 | 42.437 | 38.8% |

A separate optimized repeat measured 49.444 / 38.584 / 48.861 / 51.853 ms for
the large name/missing/source/dependency cases. The small broad-name repeat was
4.178 ms versus the initial baseline's 4.021 ms, an apparent regression. That
variability is why the headline uses the alternating comparison, rather than
claiming the first separate run's larger 23–39% gain.

Raw logs: [before](search/before.txt), [after](search/after.txt),
[repeat](search/after-repeat.txt). Samples are retained without removing outliers.
These are local synthetic workload results, not production telemetry, an FPS
measurement, or an end-to-end typing/scan/launch latency guarantee. Peak memory
was not measured. Larger projections still take tens of milliseconds.

## Validation

- Full release suite: **186 tests passed**, including the existing tests for the
  first two passes. Benchmarks are opt-in; the recorded runs above enable them.
- Differential search regression coverage: every searchable group, blank and
  whitespace queries, case, composed/decomposed Unicode, nil fields, source and
  dependency phrases, result ordering, and fresh results after inventory removal
  and reordering. Complete values are compared, not just counts.
- Comparator script rejects incomplete or duplicate search samples and differing
  result counts. Shell syntax and `git diff --check` pass.
- Local debug app packaged and launched with `./script/build_and_run.sh --verify`.
  Native checks at 1180×720 and 761×949: `TablePro` returned its application and
  newest-first history, selection opened its inspector, `GitHub` matched app
  sources and Homebrew packages, a missing query showed No Results, and Clear
  Search returned to Updates. Results refreshed when the launch scan finished.
  No Update, Install, or repository mutation action was invoked.
- Screenshots retained locally in ignored `outputs/performance/`:
  `search-desktop.png`, `search-narrow.png`, and `search-empty.png`.
  The original window size was restored and the app quit after verification.

At the end of this measurement pass, changes were local and uncommitted. No push,
published release, deployment, or production-data migration had been performed.
Subsequent Git publication is separate from these local validation results.

## Reproduce

```sh
# Current search projection: separate runs can be compared across a code change.
./scripts/benchmark-performance.sh outputs/performance/search.log search
python3 scripts/compare-performance.py --search \
  docs/performance/search/before.txt outputs/performance/search.log

# Preferred control: alternate frozen original and current implementation.
./scripts/benchmark-performance.sh outputs/performance/search-paired.log search-paired
python3 scripts/compare-performance.py --paired-search outputs/performance/search-paired.log

swift test -c release
```

The benchmark uses isolated UserDefaults suites and removes them afterward. It
never invokes scans, downloads, package commands, or installs.
