# Second performance pass — services

This pass builds on the [UI data-processing improvements](2026-08-31.md), preserving
those changes. It reduces diagnostics initialization work and release-list
preparation without changing redaction rules, version order, scan scheduling,
publisher networking, or update/install behavior.

## Review and baseline

Reviewed diagnostics persistence/redaction, application discovery, publisher
transport/cache, developer version preparation, and the global search path.
Two measured service bottlenecks warranted changes:

- Diagnostics loads retained history synchronously during store initialization.
  Loading 2,000 entries includes redacting every message, metadata key, and value.
  Every plain status string previously ran through all six regular expressions.
- Developer version selection and several registry adapters sorted strings using
  repeated shared-cache lookups inside the sort comparator. A 5,000-release list
  exceeds the 512-entry parsed-version cache, permitting repeated parsing during
  sorting. The same release list can be sorted by its adapter and again when
  selecting eligible versions.

The initial read-only discovery benchmark found 51 apps in 121.4 ms on its first
iteration and 14.6/14.7 ms on repeats. Discovery was left unchanged. Network-source
latency was not used as a benchmark because remote service state would confound
the comparison; publisher URL validation and transport limits remain intact.
Global search was inspected but not optimized or assigned a speedup claim.

The baseline includes all first-pass improvements. The three service files changed
in this pass had still matched commit `4a7307d226349fc4cf53bef27efb0539c087cd46`.
The new benchmark was executed before changing them.

## Method and results

Same macOS 27.0 (26A5416b), arm64, Apple Swift 6.3.3 and Swift Testing 6.1.3 as
the first pass; optimized `swift test -c release` builds. Compilation, fixture
creation, and assertions are outside timed regions. Each workload uses one
untimed warm-up and seven samples, reported as medians. The app was closed for
the measurements, and no scans, package commands, or network requests are used
by the benchmark. It writes only a temporary diagnostics fixture and removes it.

| Operation | Before median (ms) | After median (ms) | Reduction |
| --- | ---: | ---: | ---: |
| Load 2,000 diagnostic entries | 52.885 | 13.056 | 75.3% |
| Redact 14,000 plain strings | 41.206 | 3.950 | 90.4% |
| Redact 2,000 mixed strings | 7.716 | 2.034 | 73.6% |
| Prepare 200-release menu | 0.488 | 0.141 | 71.0% |
| Prepare 5,000-release menu | 123.885 | 13.262 | 89.3% |

- Diagnostics: the full retained limit of 2,000 entries, each with three metadata
  fields. The load measurement includes file read, JSON decoding, redaction,
  and newest-first retrieval. The benchmark checks the complete loaded entries.
- Plain redaction: 14,000 message/key/value strings without credential delimiters.
- Mixed redaction: 2,000 strings, with a query credential in every tenth string.
  Exact output and absence of the synthetic secret are asserted.
- Release menus: deterministic mixed stable, beta, platform-qualified, and build
  versions; input order is permuted. Preparation includes deduplication, retention
  of the installed/latest versions, and sorting. Output is checked against the
  scalar comparator for every sample, with 202 and 5,002 results respectively.

A repeat through the reusable runner confirmed the gains: diagnostics load
**13.123 ms**, plain redaction **4.043 ms**, mixed redaction **2.112 ms**, and
release-menu preparation **0.137 ms / 13.590 ms**. The main table keeps the first
after-run. Raw samples: [before](services/before.txt), [after](services/after.txt),
and [repeat](services/after-repeat.txt).

## Changes and safeguards

`DiagnosticRedactor` now checks for the ASCII delimiters required by every
existing rule (`:`, `=`, `-`, `_`). When none is present, none of those expressions
can match. That path still redacts the home directory and applies the same
2,000-character limit. All other strings run through the unchanged full pipeline.
The delimiter guard must be reconsidered if future rules no longer require one
of these delimiters. A differential test checks the new implementation against
the original pipeline over plain text, URL credentials, query parameters,
authorization headers, token forms, whitespace/case variants, Unicode, and
overlength strings. Existing persistence/export redaction tests still pass.

`VersionComparator.sortedNewestFirst` obtains each input's parsed value once and
retains it for that sort. Comparator calls use these immutable values directly.
The scalar and bulk paths share numeric/prerelease comparison and all tie-breaking
rules, including platform-build preference and localized string ordering. Eight
bulk sorting sites in developer package discovery/version selection use this API.
Tests cover empty/singleton input, duplicates, unknown versions, prereleases,
prefixes, long numeric components, platform/build variants, and large lists.

The sort uses temporary memory proportional to the release-list size to retain
parsed values until sorting finishes. It does not enlarge the persistent cache.
Peak RSS was not measured. Strings requiring redaction incur a small delimiter
scan before the original expressions; the mixed workload measures a 10% sensitive
case, not a guarantee for every possible log distribution.

## Verification and limits

- All **184 Release tests pass**, including the new service regressions and the
  previous transaction, security, scanner, exclusion, and lookup tests.
- Both service benchmark runs pass all assertions with matching fixture/result counts.
- The first-pass responsiveness benchmark was rerun and still passes with identical
  checksums; its samples are [retained](services/ui-regression.txt). Its results
  remain far below the original baseline; no additional speedup is attributed to
  the service changes for those workloads.
- The shared benchmark runner supports both `responsiveness` (default) and
  `services`; comparison validates seven samples per workload and matching counts.
- The updated app was built, locally ad-hoc signed, launched, and process-verified
  through `./script/build_and_run.sh --verify`. Native Diagnostics rendered 2,000
  retained entries. Developer details loaded the published versions of an npm
  package and exposed a 554-item version menu: the newest release appeared first,
  platform variants followed their matching release, and the installed version
  remained labeled. The menu was dismissed without selecting or installing a
  version. UI screenshots are ignored local artifacts under `outputs/performance/`.
- The normal launch scan reported a publisher URL safety warning for one app.
  That policy was not changed or bypassed. UI verification is not a claim that
  every remote source succeeded, and the live scan was not used for timing comparisons.
- `git diff --check` and shell syntax checks pass. The service comparison utility
  reproduces the results and rejects incomplete sample files.
- Absolute timings are subject to shared-machine load. These are local service
  workloads, not end-to-end launch, full scan, network download, or frame-rate
  measurements. The largest release fixture is a stress case, not a claim about
  every installed package's release history.

## Reproduce

```sh
./scripts/benchmark-performance.sh outputs/performance/services.log services
python3 scripts/compare-performance.py --services \
  docs/performance/services/before.txt outputs/performance/services.log
swift test -c release
```

The normal test suite skips the opt-in benchmark workload. For a benchmark-only
repeat of an already-built Release executable:

```sh
UPKEEP_SERVICE_BENCHMARK=1 swift test -c release --skip-build \
  --filter servicePerformanceBenchmark
```

At the end of this measurement pass, changes were local: no commit, push,
notarized release, or deployment had been made. Subsequent Git publication is
separate from these local validation results.
