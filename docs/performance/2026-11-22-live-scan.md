# Live full-scan benchmark, 22 November 2026

Read-only measurement of a real full scan (41 apps, 106 Homebrew packages,
107 developer packages, all sources and developer managers enabled) on an Apple
Silicon Mac with 15 cores, macOS 27.3.

Run: `UPKEEP_LIVE_SCAN_BENCHMARK=1 swift test -c release --filter liveScanBenchmark`
(`UPKEEP_LIVE_SCAN_RUNS` sets the number of full scans; default 3).

## Changes measured

- macOS: `softwareupdate --list` and `--list-full-installers` run concurrently;
  build details come from `SystemVersion.plist` instead of two `sw_vers` runs;
  automatic scans reuse a successful full-installer listing for up to 6 hours.
- npm, pnpm, Python and RubyGems run their inventory and outdated commands
  concurrently.
- VS Code extensions are checked with one batched marketplace query.

## Method

The old and new code were run alternately, three rounds of three full scans
each, after waiting for the 5-minute load average to fall below 8 (load 4–6
during the runs). The first scan in each process has cold network and tool
caches. Results depend on network and registry latency.

| | Old | New |
| --- | --- | --- |
| First scan in process (median of 3) | 3,672 ms | 2,607 ms |
| Later scans (median of 6) | 2,356 ms | 1,755 ms |

Every new-code run was faster than the old-code run in the same round. Raising
the local command limit from 8 to 12 did not help (RubyGems' `gem outdated`
sets the pace) and was not kept. An earlier set of runs taken while another
project's simulator tests held the load average near 97 was discarded.

## Follow-up: cached outdated results

RubyGems and npm now reuse their `outdated` result for up to 30 minutes while
the installed inventory output is byte-for-byte unchanged (the inventory is
still listed on every scan). In one process of four scans at load 5–6, the
first scan was 2,606 ms and later scans were 1,093, 1,582, and 990 ms; RubyGems
fell from about 1.4 s to 0.15–0.35 s and npm from about 1.1 s to 0.5 s. The
1,582 ms run was held by a slower `softwareupdate` response. Python's pip
checks (about 1 s) now set the pace of repeat scans.

## Follow-up: Python and on-disk caches

Python's pip checks use the same inventory-keyed cache. The packaged app now
keeps the outdated results (`developer-outdated.json`) and the macOS
full-installer listing (`macos-installers.json`) in
`~/Library/Caches/nz.haydenthorn.Upkeep/`; tests and benchmarks stay in memory.
Measured with the installed app's own scan log at load 7–8: the first check
after launch took 2,755 and 2,448 ms before the caches existed, and 1,098, 987,
and 1,345 ms on three later relaunches.

## Follow-up: cask catalog and macOS listing

Each scan previously read and fully decoded the cached 19 MB Homebrew cask
catalog API response (7,846 casks) and kept five fields per cask. The cache now
stores only those fields (468 KB) and keeps the decoded catalog in memory until
the file changes; the isolated catalog phase went from about 156 ms to 0 ms.
Automatic scans also reuse a successful `softwareupdate --list` result for an
hour (the macOS page always checks again), removing the slowest and most
variable step (0.75–1.9 s).

Live benchmark at load 4–5: later scans were 652, 700, and 658 ms (previously
763, 1,874, and 752 ms, with the slow run held by `softwareupdate`). Homebrew
inventory (about 0.65 s) now sets the pace.

Installed app, measured with `footprint` about 10 s after the launch check
completed: 351 MB before (147 MB small and 88 MB large allocations, 64 MB images)
and 214 MB after (98 MB small allocations, no large allocations, the same 64 MB
of window images). First checks after relaunch took 1,017–1,137 ms.

## Install size and memory

Installed app size went from 20 MB to 10 MB and the download from 8.6 MB to
6.8 MB. The release binary had kept its debug symbols (15.2 MB, of which 6 MB
was code); release packaging now saves them to `outputs/Upkeep.app.dSYM` and
strips the binary (6.3 MB). Building the app target with `-Osize` saved another
1 MB (5.4 MB binary) with no measurable change in the list, search, or
responsiveness benchmarks (list 1.85 vs 1.88 ms, search 39.3 vs 39.1 ms, rebuild
4.7 vs 5.1 ms at 2,000 items) or in live scans (later scans 629–638 ms).

Memory was traced every 0.5 s from launch on the installed app (load 4–10).
The launch check itself was not the peak; the CVE check that follows it was.
It downloaded Homebrew's 79 MB advisory feed into memory and decoded all of it,
although only 4 of 93 installed formulae have advisories (about 415 KB). The
feed is now downloaded to a file, memory-mapped, and scanned for the installed
formulae only (verified identical to a full decode for all 598 formulae in the
live feed). Upkeep also asks malloc to return free pages after a scan, after
loading the feed, and after a CVE check.

| | 0.25.4 | Now |
| --- | --- | --- |
| Peak footprint | 495–552 MB | 355 MB |
| Footprint 30–90 s after launch | 264 MB (90 s) | 204–207 MB |
| After the CVE check completes | 216 MB | 192 MB |

About 64 MB of the remainder is window drawing buffers that the offline test
fixture shows as well; the live heap is about 63 MB, mostly SwiftUI.
